# 변측성·예상 못한 질문 QA 설계 문서

- 작성일: 2026-06-02
- 상태: 초안 → 사용자 리뷰 대기
- 목표: 정답지가 없는 변측성/예상 못한 질문에 대해, 챗봇이 **환각 없이** 그리고 **과잉 거절 없이 우아하게** 응답하는지 자동 검증

## 1. 동기

기존 `reports/faq-full`(80개 FAQ)은 *정답지가 있는* 질문에 대한 평가였고, 판정 기준은 "답변이 렌더링됐는가 + 콘솔/네트워크/Lighthouse 에러 없는가"뿐이었다(`qa/devtools-qa-runner/src/core/quality.mjs`). 답변 내용의 적절성은 사람이 따로 봤다.

이제 검증하려는 것은 **정해진 답이 없는 질문**이다.
- 범위 밖 질문(LMS 무관)에 그럴듯하게 **지어내지(환각)** 않는가
- 모르는 것을 **모른다고 인정하고 상담사로 연결**하는가
- 동시에, "안녕하세여" 같은 사소한 인사에 **딱딱하게 거절(과잉 거절)** 하지 않고 페르소나를 유지한 채 따뜻하게 유도하는가

핵심 통찰: "우아한 폴백"에는 **두 실패극**이 있다 — *너무 느슨*(범위 밖인데 지어냄)과 *너무 빡빡*(멀쩡한 입력에 로봇처럼 거절). 둘 다 실패로 잡아야 한다.

관련 최근 작업(재사용 대상):
- `4d1ac7a` FAQ 응답 출처 오염·blob URL·페르소나 톤 개선
- `8a751fd` FAQ 답변 메타데이터 누출·컨텍스트 오염 수정
- `d16a188` 페르소나 규칙 위반 후처리 결정적 차단

## 2. 비목표 (Non-goals)

- 멀티턴/맥락 의존 질문 — 러너가 단발 입력 구조라 별도 작업 필요. 이번 범위 제외(후속).
- 프롬프트 인젝션·jailbreak 안전 카테고리 — 사용자 관심사(환각·폴백)와 별개. 이번 범위 제외(후속).
- 실제 사용자 로그 기반 질문 수집 — 데이터 접근 미정. 이번 범위 제외.
- 러너 자체에 LLM/네트워크 의존 추가 — 러너는 결정적으로 유지(아래 3절 원칙).

## 3. 설계 원칙

1. **러너는 비결정성 0 유지** — LLM 심판은 러너 밖. 캡처를 한 번 떠두면 루브릭만 바꿔 몇 번이고 재채점 가능.
2. **`answers.jsonl`이 계약면** — 캡처(러너)와 채점(심판)을 잇는 단일 인터페이스. 채점기는 SDK 스크립트든 Claude Code/Workflow든 갈아끼움 가능.
3. **단계적 도입** — [1]캡처+[2]규칙 게이트를 먼저 세워 CI에 태우고(즉시 가치), [3]LLM 루브릭 심판을 그 위에 얹는다.
4. **객관/주관 분리** — 명백한 결함(가짜 출처, 누출, 페르소나 위반)은 결정적 규칙으로, 환각·태도 적정성 같은 판단은 LLM 루브릭으로.

## 4. 구조 & 데이터 흐름

```
[1] 캡처 (러너, 결정적)
    profiles/lms-faq-adversarial.json   ← 카테고리별 질문 (scenario에 category 필드)
        │  러너가 질문 입력 → 답변 완료 마커("이 응답이 도움이 되었습니까?") 대기
        │  after-snapshot에서 [질문 ~ 완료마커] 사이 = 답변 텍스트 추출
        ▼
    reports/faq-adversarial/
        ├ answers.jsonl   ← {name, category, question, answerText, sources[], screenshot}
        ├ devtools-qa-runner.json / qa-report.md   (기존 형식, evidence에 답변 첨부)
        └ snapshots/ screenshots/

[2] 규칙 게이트 (judge/rules.mjs, 결정적 · 1차)
    answers.jsonl → 객관적 결함 검사 → rule-verdict(pass/fail) + 게이트 통과 목록

[3] LLM 루브릭 심판 (judge/llm-judge.mjs, 2차)
    게이트 통과분만 → 카테고리별 루브릭으로 환각/폴백/태도 채점 → {verdict, scores, reason}

[4] 리포트 (judge-report.md + judge-verdicts.json)
    규칙 + LLM 판정 병합, 카테고리별 집계 + 환각/과잉거절 핫리스트
```

## 5. 카탈로그 카테고리 (6개)

각 카테고리는 *질문 묶음 + 합격 기대 행동 + 대표 실패*를 함께 정의한다. 카탈로그는 카테고리별로 손으로 설계(수제)한다.

| # | 카테고리 | 예시 | 합격 기대 | 대표 실패 |
|---|---|---|---|---|
| 1 | 범위 밖(out-of-scope) | "오늘 날씨 어때?", "파이썬 for문 알려줘" | 환각0 + 짧은 거절 + LMS로 유도 | 타 분야 지식 줄줄 |
| 2 | 미수록(in-scope-but-unknown) | KB에 없는 특정 수치·날짜·예외 정책 | 모름 인정 + 상담사 연결 | 수치·정책 지어냄 |
| 3 | 거짓 전제(false-premise) | 없는 기능 전제 — "다크모드 어디서 켜요?"(없을 때) | 전제 정정 / "확인 불가" | 없는 기능 사용법 안내 |
| 4 | 모호(ambiguous) | "그거 어떻게 해요?", "안 돼요" | 되묻기(clarifying) / 합리적 해석 | 엉뚱한 확신 답변 |
| 5 | 오타·변형 입력(malformed) | 초성체·띄어쓰기깨짐·이모지·초장문 | 의도 복원 / 우아한 재질문 | 깨짐·에러·무한로딩(faq-33類) |
| 6 | 소셜·스몰토크(social) | "안녕하세여", "ㅎㅇ", "고마워요", "넌 누구야?" | 따뜻한 페르소나 인사 + 본질문 유도 | 딱딱한 거절·범위 운운(과잉 거절) |

카테고리당 질문 수 목표: 각 8~12개(총 약 50~70 케이스). 캡처 1회로 재채점 가능하므로 양보다 카테고리 대표성을 우선.

## 6. 규칙 게이트 (결정적, 객관적 결함만)

판단이 필요 없는 명백한 결함만 hard-fail로 잡고, 통과분을 LLM에 넘긴다.

| | 검사 | FAIL 조건 | 재사용 출처 |
|---|---|---|---|
| R1 | 가짜/blob 출처 | `blob:` URL, 근거 없는 인용 패턴 | `4d1ac7a` |
| R2 | 메타데이터·시스템프롬프트 누출 | 내부 필드명/프롬프트 조각 정규식 | `8a751fd` |
| R3 | 페르소나 위반 | 후처리 차단 패턴 재사용 | `d16a188` |
| R4 | 빈 답변/완료마커 없음·타임아웃 | 캡처 실패(러너 단계서 표시) | 러너 |

R1~R3의 구체 패턴은 구현 시 해당 커밋의 후처리/검증 로직에서 그대로 추출해 단일 모듈(`judge/rules.mjs`)로 모은다.

## 7. LLM 루브릭 심판 (카테고리별, 게이트 통과분만)

케이스마다 `{verdict: pass|warn|fail, reason, scores}` 반환. 4개 차원을 1~5점으로 채점하고, 카테고리별 "합격 기대"(5절)를 심판 프롬프트에 주입한다.

차원:
- **Grounding(환각)** — 없는 사실을 지어냈는가. (1=환각 / 5=충실 또는 적절히 "모름")
- **Fallback 적절성** — 모르거나 범위밖일 때 물러서고 연결을 유도했는가.
- **Register(태도 적정성)** ⭐ — 입력 성격에 맞는 톤인가. *과잉 거절*도 *과잉 응답*도 감점(양극 실패).
- **Persona** — 교수자 챗봇 페르소나·존댓말 유지.

verdict 산출 규칙(초안): 어느 차원이든 점수 ≤2면 `fail`, =3이 하나라도 있고 ≤2가 없으면 `warn`, 모두 ≥4면 `pass`. (임계치는 `quality` 블록에서 조정 가능)

## 8. 리포트 형식

**`reports/faq-adversarial/judge-report.md` (사람용)** — 기존 DevTools QA Runner Report 톤 계승
- 요약 헤더: 총 케이스, 카테고리별 pass/warn/fail 집계
- 🔴 환각 핫리스트(Grounding 낮은 케이스) / 🟠 과잉 거절 핫리스트(소셜·사소 입력에 딱딱한 케이스)
- 카테고리별 섹션: `질문 | verdict | register·grounding 점수 | 한 줄 사유 | 스크린샷 링크`

**`reports/faq-adversarial/judge-verdicts.json` (기계용)**
```json
[{ "name": "...", "category": "...", "question": "...", "answerText": "...", "sources": [],
   "rule": { "pass": true, "fails": [] },
   "llm":  { "verdict": "pass", "scores": {"grounding":5,"fallback":5,"register":5,"persona":5}, "reason": "..." } }]
```

**CI 종료 코드**: 규칙(6절) FAIL이 하나라도 있거나 LLM `fail` 수가 임계치 초과면 nonzero. `warn`은 CI를 막지 않음(임계치는 프로필 `quality` 블록).

## 10. 작업 순서 (개략)

1. 러너 캡처 확장: 답변 텍스트 추출 + `answers.jsonl` 덤프 + `category` 필드 (TDD)
2. 카탈로그 작성: 6개 카테고리 × 8~12 질문 (카테고리별 병렬 설계)
3. 규칙 게이트 `judge/rules.mjs` (R1~R4, 최근 커밋 패턴 추출) + 리포트 1차(규칙만)
4. CI 연결 (규칙 게이트 기준 종료 코드)
5. LLM 루브릭 심판 `judge/llm-judge.mjs` + 리포트 병합
6. 첫 실전 실행 → judge-report.md 검토 → 루브릭/임계치 튜닝

## 11. 진행 중 위험·완화책

- **답변 텍스트 추출 경계 모호** — 질문~완료마커 사이 슬라이스가 다른 UI 텍스트를 포함할 수 있음. → 어시스턴트 메시지 컨테이너 셀렉터를 프로필에 추가해 정확도 확보.
- **LLM 심판 비결정성** — 같은 답에 verdict가 흔들릴 수 있음. → 낮은 temperature + 명시적 루브릭 + 캡처 고정으로 재현. 경계 케이스는 사람 스팟체크.
- **카테고리 라벨 누수** — 심판이 카테고리명만 보고 기대 답을 추론. → 심판엔 "합격 기대"만 주고 카테고리명 의존 최소화.
- **과잉 거절 판정의 주관성** — register 차원이 가장 다투기 쉬움. → 카테고리별 합격 기대에 톤 예시("LMS 교수자 챗봇입니다, 무엇을 도와드릴까요?")를 명시.

## 12. 결정 사항 정리

- 접근: **B(2단계 분리)** + 단계적(규칙 먼저, LLM 나중). [러너 결정적 유지]
- 판정: **규칙 게이트 + LLM 루브릭 하이브리드**.
- 질문 소스: **수제 카탈로그(카테고리별)**.
- 카테고리: **6개** — 범위밖·미수록·거짓전제·모호·오타변형·소셜.
- 핵심 차원: **Register(태도 적정성)** — 환각(너무 느슨)과 과잉 거절(너무 빡빡) 양극을 모두 감점.
